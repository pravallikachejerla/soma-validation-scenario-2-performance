Summary Verdict

What improved: Database query count (72× on large, 13× on medium), medium-profile p95 latency (24–40×), medium-profile throughput (1.1–1.7×).

What regressed: Large-profile p95/p99 tail latency (2–3× slower), large-profile throughput (23–41% slower), small-profile p95 (2× slower).

What is within noise: p50 latency across all profiles, memory allocation on large and small profiles.

Why the in-memory regression on large profile: The candidate removes the global evalMu mutex and replaces 500 per-candidate condition loads with a single batch load. In the in-memory backend, the mutex was masking the real per-request work. Without the mutex, the engine now does the full evaluation work in parallel, which exposes the actual CPU cost of rule compilation and candidate evaluation. In production with PostgreSQL, the 72× query reduction (253 → 3.52 round-trips) would dominate and the latency should improve — but this has not been measured.

Promotion recommendation: Not recommended for promotion on in-memory evidence alone. The candidate should be validated against PostgreSQL with production-equivalent network latency before promotion. The query-count reduction is real and significant, but the in-memory latency regression means we cannot claim a P95 improvement.
