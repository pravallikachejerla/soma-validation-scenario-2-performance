What the candidate changed

The baseline calls LoadConditions(promotionID) once per candidate in a loop (N+1 pattern). The candidate calls LoadAllConditions(promotionIDs) once per request, returning all conditions in a single map lookup.

// Baseline (N+1):
for _, promo := range candidates {
    conds, _ := store.LoadConditions(ctx, promo.ID)  // 1 query per candidate
    ...
}

// Candidate (batch):
allConds, _ := store.LoadAllConditions(ctx, candidateIDs)  // 1 query total
for _, promo := range candidates {
    conds := allConds[promo.ID]  // map lookup, no query
    ...
}

Production relevance

The in-memory benchmark instruments the store to count query calls. In production with PostgreSQL, each query is a network round-trip (~1–3ms RTT). The 72× query reduction at large profile would save approximately 250 × 2ms = 500ms per request in production latency. This is the candidate's primary value proposition.

Not evaluated: The PostgreSQL path was not benchmarked in this run. The in-memory numbers above measure query call count, not wall-clock latency savings. The production latency improvement is projected, not measured.

Query plan evidence

The PostgreSQL query plan for LoadAllConditions uses the existing index idx_promotion_conditions ON promotion_conditions (promotion_id). With 500 promotion IDs in the IN clause, PostgreSQL will use an index scan. No new indexes are required.
